SmartMarket SV — de la pantalla a la base de datos

Un mapa de las 4 capas del sistema: quién lo usa, qué procesos atraviesa, dónde vive el dato, y cómo se audita cada decisión. Construido con nombres reales de tablas, controladores y componentes — no una arquitectura idealizada.

Nota de honestidad: este atlas usa números reales del proyecto (13 tablas documentadas, 2 roles activos), no las cifras genéricas de un sistema enterprise. Un dato inventado, aunque se vea más impresionante, contradice el principio que rige todo SmartMarket SV: nunca presentar como hecho algo que no se puede verificar.

Capa 1 · Experiencias

Roles y superficies

Dos roles humanos activos, uno reservado, y un actor automatizado que participa en la misma historia operacional sin ser un rol de usuario.

Rol activo

👤 Usuario

App pública (React). Busca productos, arma listas de compra, compara supermercados, ve historial de precios y recomendaciones del Sistema Experto.

rol: usuario
Rol activo

🛠️ Administrador

Panel Filament (/admin). Carga catálogo y precios manuales, cura los datos del extractor (Publicar/Rechazar), gestiona usuarios.

rol: admin + estado: activo
Reservado a futuro

🧩 Moderador

Existe como valor de rol en la base de datos desde una fase anterior, pero sin políticas de permisos definidas todavía en el gate del panel.

sin permisos aún
Un actor no-humano: el Sistema Experto (Python) participa en la misma historia operacional — recibe los hechos de una alternativa, evalúa reglas, y devuelve una recomendación — pero no es un "rol" del sistema: no tiene sesión, no inicia sesión, no tiene UI propia. Es un servicio que Laravel consulta, nunca al revés.

Concurrencia sobre la misma historia

Un Administrador puede estar corrigiendo el precio de "Leche Foremost 1L" en Filament, mientras un Usuario compara esa misma lista en tiempo real. El PrecioActualObserver archiva el cambio en historial_precios automáticamente; la próxima optimización del usuario ya ve el precio actualizado — sin que ninguno de los dos sepa que el otro está activo en ese momento.

Capa 2 · Procesos

Ciclo de vida de una lista de compra

Caso real trazado con IDs verdaderos de una corrida capturada durante las pruebas del proyecto.

ListaCompra #20 · "Lista Experto Test"

El usuario crea una lista con presupuesto $50.00 y agrega productos vía ListaCompraController::agregarProducto.

POST /api/listas/20/optimizar

OptimizationService compara 4 alternativas (Súper Selectos ×2, Walmart, PriceSmart) vía ComparisonService + DistanceService.

Por alternativa → ExpertSystemService::recommend()

Cada alternativa se traduce a 13 hechos y se envía a Python. Una recibió nivel_recomendacion: NO_RECOMENDABLE (regla R02, esenciales faltantes).

resultados_optimizacion #27 (persistido)

El resultado completo, incluida la recomendación de cada alternativa, se guarda en resultado_json.

React · CompararView

El usuario ve el podio de resultados con el ExpertRecommendationBadge por alternativa — lenguaje natural, sin códigos de regla.

POST /api/listas/20/chat (opcional)

El usuario pregunta "¿por qué no es recomendable?" — Laravel reconstruye los hechos desde resultado_json y consulta /api/v1/chat.

Estados

Entra a producto_raw

Nunca se sobrescribe

Capa 4 · Auditoría

Modo técnico

Haz clic en cualquier tarjeta de la sección siguiente para revelar la ruta exacta del dato — de la pantalla a la tabla.

En un sistema de 13 tablas, la ruta completa de cualquier dato es corta y rastreable a mano — no hace falta un motor de grafos. Este atlas la muestra directamente: cada pregunta de control revela su cadena real de componentes.
Capa 4 · Auditoría

3 preguntas de control

Lo que un stakeholder pregunta en una reunión — y cómo el atlas responde con la ruta exacta.

¿Quién decidió que esta alternativa NO es recomendable?›
CompararView.tsx→ ListaCompraController::optimizar→ OptimizationService→ ExpertSystemService::recommend()→ Sistema Experto · regla R02→ resultados_optimizacion.resultado_json

Respuesta directa: winning_rule: "R02", prioridad_aplicada: "DISPONIBILIDAD" — nadie del equipo "decidió" a mano, la regla se disparó porque faltan_esenciales = true.

¿Qué pasa si el servicio de Python falla en producción?›
ExpertSystemService→ timeout 3s × 2 intentos→ fallback: expert_system_available=false→ React sigue mostrando la optimización

La optimización de Laravel es independiente del Sistema Experto — nunca bloquea al usuario. Ver Atlas del Sistema Experto para el detalle completo del fallback.

¿Qué campo de la base de datos cambió cuando el admin editó un precio?›
Filament · PrecioActualResource→ PrecioActualObserver::updating()→ historial_precios (INSERT append-only)→ precios_actuales (UPDATE)

El precio anterior nunca se pierde — el observer lo archiva automáticamente antes de que precios_actuales se sobrescriba. Es la misma tabla que alimenta el gráfico de PriceHistoryChart.
